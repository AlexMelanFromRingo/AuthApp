# Конституція проєкту «Комплекс засобів аутентифікації»

Android-додаток (TOTP-аутентифікатор) та Web-стенд для демонстрації —
дипломна робота бакалавра з кібербезпеки.

## Core Principles

### I. Безпека понад усе (NON-NEGOTIABLE)

Додаток MUST відповідати найвищим стандартам інформаційної безпеки:

- Усі секрети (TOTP-ключі, налаштування облікових записів) MUST зберігатися
  лише у зашифрованому локальному сховищі (EncryptedSharedPreferences або
  зашифрована Room-БД), ключі шифрування MUST генеруватися та зберігатися в
  Android Keystore і MUST NOT покидати апаратне сховище.
- Доступ до додатку MUST здійснюватися СУВОРО через BiometricPrompt
  (відбиток пальця / розпізнавання обличчя); обхід біометричного бар'єра
  у release-збірці заборонений.
- Секрети MUST NOT потрапляти у логи, скріншоти (FLAG_SECURE), бекапи
  (`android:allowBackup="false"`) чи буфер обміну без явної дії користувача.

**Обґрунтування**: тема дипломної роботи — засоби аутентифікації; компрометація
секретів знецінює і продукт, і дослідження.

### II. Криптографічне ядро

Ядро генерації одноразових паролів MUST реалізовувати RFC 6238 (TOTP) на базі
RFC 4226 (HOTP):

- Стандартні алгоритми: HMAC-SHA-1, HMAC-SHA-256, HMAC-SHA-512 — MUST.
- Розширені хеш-функції: BLAKE2s, BLAKE2b, BLAKE3, SHA3 — MUST підтримуватися
  ядром нарівні зі стандартними.
- Коректність кожного алгоритму MUST підтверджуватися тестовими векторами
  (RFC 6238 Appendix B для стандартних; еталонні реалізації для розширених).
- Криптографічні примітиви MUST братися з перевірених бібліотек; власноруч
  написані реалізації хеш-функцій заборонені.

**Обґрунтування**: розширений набір хеш-функцій — наукова новизна роботи,
тому його коректність має бути доказовою, а не декларативною.

### III. Монорепозиторій

Проєкт MUST складатися з двох частин в одному репозиторії:

- `android-app/` — нативний Android-додаток (Kotlin).
- `web-stand/` — статичний сайт-стенд, придатний для розгортання на
  GitHub Pages (без серверної частини).
- Спільні артефакти (тестові вектори, документація алгоритмів) MUST лежати
  на верхньому рівні або дублюватися узгоджено; розбіжність між частинами
  вважається дефектом.

**Обґрунтування**: єдиний репозиторій спрощує синхронізацію демонстраційного
стенда з додатком та подання роботи на захист.

### IV. UI/UX та локалізація

- Інтерфейс додатку MUST бути написаний на Jetpack Compose з використанням
  Material Design 3 (Material You, динамічні кольори де доступно).
- Використання XML-layout чи View-based UI для екранів додатку заборонене.
- Усі тексти інтерфейсу, логи та коментарі в коді додатку і на сайті MUST
  бути виключно українською мовою. Англійська допускається лише в
  ідентифікаторах коду, назвах API та усталених технічних термінах без
  українського відповідника.

**Обґрунтування**: вимога локалізації випливає зі статусу кваліфікаційної
роботи УДУНТ; єдиний UI-стек гарантує цілісність дизайну.

## Технологічні обмеження

- Android: Kotlin, Jetpack Compose, Material 3, AndroidX Biometric,
  AndroidX Security (EncryptedSharedPreferences) або Room із SQLCipher;
  Android Keystore для ключового матеріалу.
- Web-стенд: лише статичні файли (HTML/CSS/JS), сумісні з GitHub Pages;
  жодних серверних залежностей чи зовнішніх трекерів.
- Секрети, ключі підпису та keystore-файли MUST NOT комітитися в репозиторій.
- Залежності MUST мати зафіксовані версії (version catalog / lock-файли).

## Процес розробки та контроль якості

- Кожна зміна криптографічного ядра MUST супроводжуватися проходженням
  повного набору тестових векторів до злиття.
- Функціонал безпеки (Принцип I) MUST покриватися автоматизованими тестами
  там, де це технічно можливо; решта — задокументованими ручними перевірками.
- Code review (само-рев'ю через диф перед комітом — мінімум) MUST перевіряти
  відповідність Принципам I–IV; порушення блокує зміну.
- Демонстраційний Web-стенд MUST оновлюватися синхронно зі змінами
  алгоритмів ядра, щоб стенд завжди відображав фактичну поведінку додатку.

## Governance

- Ця конституція має пріоритет над усіма іншими практиками проєкту; у разі
  конфлікту з іншими документами діє конституція.
- Поправки вносяться через зміну цього файлу з обов'язковим оновленням
  версії та Sync Impact Report; зміни, що послаблюють Принцип I, MUST бути
  явно обґрунтовані вимогами дипломної роботи.
- Версіонування: MAJOR — видалення чи несумісна зміна принципу; MINOR —
  новий принцип або суттєве розширення; PATCH — уточнення формулювань.
- Перевірка відповідності: кожен plan-документ (Constitution Check) MUST
  звірятися з чинною версією конституції; відхилення фіксуються в
  Complexity Tracking з обґрунтуванням.
