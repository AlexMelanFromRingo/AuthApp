# Research: Комплекс засобів аутентифікації (TOTP/OCRA)

**Дата**: 2026-06-09 | **Гілка специфікації**: `001-totp-ocra-auth`

Усі NEEDS CLARIFICATION з Technical Context вирішено нижче. Формат:
Рішення / Обґрунтування / Розглянуті альтернативи.

## R1. Криптографічна бібліотека для Android (розширені хеші)

**Рішення**: Bouncy Castle (`org.bouncycastle:bcprov-jdk18on`) як єдиний
постачальник розширених алгоритмів: `Blake2sDigest`, `Blake2bDigest`
(нативний keyed-режим у конструкторі), `Blake3Digest` (keyed-ініціалізація),
SHA3 + `HmacSHA3-256`. Стандартні HMAC-SHA1/256/512 — через системний
`javax.crypto.Mac` (проходження векторів RFC 6238 гарантоване платформою).

**Обґрунтування**: одна перевірена бібліотека покриває всі 4 розширені
алгоритми, включно з keyed-режимами BLAKE2/BLAKE3, що прямо вимагає FR-008;
відповідає Принципу II конституції (заборона самописних хеш-реалізацій).

**Альтернативи**: окремі Kotlin-реалізації (kotlincrypto.hash) — більше
залежностей, немає Blake3 keyed на момент аналізу; JNI-обгортки (libsodium)
— ускладнюють збірку і не дають SHA3/BLAKE2s одночасно.

## R2. Криптографія Web-стенду

**Рішення**: `@noble/hashes` (чистий JS, аудитований) замість crypto-js і
blake3-js: модулі `sha1/sha256/sha512/sha3/blake2s/blake2b/blake3/hmac`
покривають усі 7 алгоритмів і обидві конструкції MAC (keyed + HMAC).

**Обґрунтування**: crypto-js не підтримує BLAKE-сімейство і фактично не
розвивається; blake3-js тягне WASM, що ускладнює статичний деплой на
GitHub Pages. Одна залежність без WASM = простіший статичний сайт (FR-020)
і симетрія з Bouncy Castle на Android для звірки векторів.

**Альтернативи**: Web Crypto API — немає SHA3/BLAKE взагалі; окремий
blake3-wasm — швидший, але швидкість тут не критична (одиничні обчислення).

## R3. Стек Web-стенду

**Рішення**: Vite + vanilla JS (ES-модулі) + TailwindCSS; генерація QR —
пакет `qrcode` (canvas); тести — Vitest. Збірка `npm run build` → `dist/`
деплоїться на GitHub Pages через GitHub Actions.

**Обґрунтування**: стенд має 3 екрани без складного стану — фреймворк (Vue)
не виправданий; Vite дає dev-сервер, мініфікацію і статичний вихід без
бекенду (FR-020). Сканування QR стенду не потрібне (він лише показує QR і
приймає введені коди).

**Альтернативи**: Vue 3 + Vite — зайвий шар для 3 сторінок; чистий HTML без
збірки — втрачаємо npm-залежності (@noble/hashes) і тести.

## R4. Локальне сховище Android

**Рішення**: `EncryptedSharedPreferences` (androidx.security-crypto,
останній стабільний 1.1.x) з майстер-ключем AES-256-GCM в Android Keystore;
записи токенів — JSON-серіалізовані значення (kotlinx.serialization).
Біометричний бар'єр — на рівні застосунку: `BiometricPrompt`
(BIOMETRIC_STRONG) під час запуску і повернення з фону; майстер-ключ БЕЗ
`setUserAuthenticationRequired`.

**Обґрунтування**: явний вибір замовника (стек у вхідних даних) і Принцип I
конституції. Прив'язка ключа до автентифікації
(`setUserAuthenticationRequired(true)`) відхилена свідомо: зміна реєстрації
біометрії інвалідовує ключ і безповоротно знищує всі токени, що суперечить
edge-case специфікації («пояснити, що зробити», а не «втратити все»). Це
стандартний компроміс аутентифікаторів (той самий патерн у Aegis).
Задокументований ризик: security-crypto переведено в режим супроводу;
для дипломного проєкту API стабільний і достатній, міграція на DataStore +
власний Keystore-шар — поза межами версії.

**Альтернативи**: Room + SQLCipher — другий криптошар і нативна залежність
заради ~100 записів не виправдані; DataStore + ручний AES-GCM — більше
самописного криптокоду, що збільшує площу помилок.

## R5. KDF та AEAD для пакета міграції

**Рішення**: Argon2id через Bouncy Castle `Argon2BytesGenerator`
(чиста JVM-реалізація): m=64 MiB, t=3, p=4, сіль 16 Б, вихід 64 Б →
HKDF-SHA256 розщеплює на K_enc (32 Б, info=`authapp-migration-enc`) та
K_rcpt (32 Б, info=`authapp-migration-receipt`). Шифрування пакета —
AES-256-GCM (`javax.crypto`), квитанція — HMAC-SHA256(K_rcpt,
SHA-256(маніфест) ‖ nonce експорту).

**Обґрунтування**: memory-hard KDF вимагає FR-016; Argon2id у BC не додає
нових залежностей (BC уже в проєкті через R1). Розщеплення через HKDF дає
криптографічно незалежні ключі шифрування і квитанції з однієї парольної
фрази (FR-018). Web-стенд участі в міграції не бере — JS-реалізація KDF не
потрібна.

**Альтернативи**: PBKDF2 — не memory-hard, відхилено вимогою FR-016;
argon2kt (JNI) — швидший, але нативна залежність без потреби (експорт —
одинична операція, секунда обчислення прийнятна).

## R6. Багатокадровий QR для міграції

**Рішення**: кадри `authapp://migrate?v=1&i=<номер>&n=<всього>&data=...`,
корисне навантаження кадру ≤ 512 байтів base64url, рівень корекції M.
Кадр 1 — заголовок (версія, pid, сіль, параметри Argon2, nonce GCM),
решта — фрагменти шифротексту. Альтернативний канал — той самий пакет
одним файлом через системний share.

**Обґрунтування**: 512 Б base64url ≈ QR версії 17–20 — впевнено сканується
камерою смартфона; нумерація i/n реалізує edge-case дозбирання пропущених
кадрів (FR-017).

**Альтернативи**: анімований QR (fountain codes, як UR-формат) — цікаво, але
надлишково для ≤100 токенів; один гігантський QR — нечитабельний понад
~2 КБ.

## R7. Тестові вектори розширених алгоритмів

**Рішення**: референсний Python-скрипт `shared/test-vectors/generate.py`
(hashlib: sha3, blake2; пакет blake3) генерує JSON-вектори: TOTP для всіх
7 алгоритмів × довжини 6/8/9/10, окремі вектори узагальненого усічення
(MAC → offset → код), OCRA-вектори RFC 6287 (скопійовані з RFC) + власні
для часових профілів. JSON-файли — спільний артефакт: їх читають і
Kotlin-тести (core-crypto), і Vitest (web-stand).

**Обґрунтування**: FR-010 вимагає незалежну референсну реалізацію; Python
hashlib/blake3 — третя незалежна кодова база відносно BC і noble, тож збіг
трьох реалізацій є сильним доказом коректності (Принцип II).

**Альтернативи**: вектори вручну — нема незалежного підтвердження; лише
крос-тест Kotlin↔JS — спільна помилка інтерпретації залишилася б непомітною.

## R8. Версії платформи Android

**Рішення**: minSdk 26 (Android 8.0), targetSdk 35, Kotlin 2.x, JDK 17,
Compose BOM (Material 3), CameraX + ML Kit `barcode-scanning` для
сканування QR, androidx.biometric (BIOMETRIC_STRONG).

**Обґрунтування**: API 26 дає java.time без desugaring і стабільний
Keystore; покриття пристроїв > 95%. Динамічні кольори Material You —
з API 31, з фолбеком статичної схеми нижче (Принцип IV). ML Kit on-device,
мережі не потребує.

**Альтернативи**: minSdk 23 — ускладнює Keystore-логіку заради маргінального
покриття; ZXing замість ML Kit — простіший, але гірше розпізнає у поганому
освітленні; ML Kit явно запитаний замовником.

## R9. Структура Android-проєкту та ітерації

**Рішення**: два Gradle-модулі: `:core-crypto` — чистий Kotlin/JVM модуль
(HOTP/TOTP/OCRA, усічення, MAC-фабрика, кодеки Base32/URI; нульова
залежність від Android SDK) та `:app` — Compose UI, сховище, біометрія,
камера, міграція. Розробка ітераціями: 1) core-crypto + вектори;
2) web-stand ядро + ті самі вектори; 3) сховище+біометрія+список/додавання;
4) демо-цикл TOTP зі стендом; 5) OCRA; 6) міграція; 7) гартування безпеки.

**Обґрунтування**: чистий JVM-модуль тестується без емулятора (швидкий
TDD за векторами) і відповідає вимозі замовника «починаючи з
криптографічного ядра на Kotlin».

**Альтернативи**: один модуль `:app` — криптотести повільніші і брудніші;
Kotlin Multiplatform для шарингу ядра з web — привабливо, але подвоює
складність збірки; незалежна JS-реалізація, звірена векторами, доказово
еквівалентна.
